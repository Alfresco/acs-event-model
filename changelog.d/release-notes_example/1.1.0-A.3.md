# 1.1.0-A.3 release details

Released 2026-09-29. Summary: [CHANGELOG](../CHANGELOG_example.md#110-a3---2026-09-29)

## Added

### ACS-12674: Permanent delete flag in node deleted events

`org.alfresco.event.node.Deleted` events now carry an optional `isPermanentlyDeleted` flag in `data.resource`,
so consumers can tell a node moved to the trashcan apart from a node that is gone for good.

| Value    | Meaning                                                              |
|----------|----------------------------------------------------------------------|
| `true`   | The node was permanently deleted and cannot be restored.             |
| `false`  | The node was moved to the trashcan and can still be restored.        |
| _absent_ | The emitting ACS version cannot distinguish the two. Treat as unknown. |

Example `data.resource` fragment:

```json
{
  "@type": "NodeResource",
  "id": "fe554533-0fdd-4db3-9545-330fddcdb34f",
  "name": "test.docx",
  "isFile": true,
  "isFolder": false,
  "isPermanentlyDeleted": false
}
```

**Java API.** `NodeResource.isPermanentlyDeleted()` returns a `Boolean` (nullable) and
`NodeResource.Builder.setIsPermanentlyDeleted(Boolean)` sets it. `toBuilder()` copies the value.

**JSON schema.** `nodeDeleted.json` declares `isPermanentlyDeleted` as an optional `boolean`.

**Compatibility.** The field is additive. The model's default mappers ignore unknown properties, so consumers
on older `acs-event-model` versions keep working and simply do not see the flag. Consumers that deserialize
with their own strict mapper (`FAIL_ON_UNKNOWN_PROPERTIES` enabled) should upgrade before ACS starts emitting it.
Do not treat a missing flag as `false`.

## Fixed

### ACS-12674: `NodeResource.equals()` now compares `primaryAssocQName`

`primaryAssocQName` was already part of `NodeResource.hashCode()` but was missing from `equals()`.
Two resources that differed only by primary association QName were therefore considered equal,
which broke the `equals`/`hashCode` contract.

**Impact.** Code that compares `NodeResource` instances, or keeps them in `Set`s or as `Map` keys,
may now treat resources as different where it previously treated them as equal. No change to the JSON payload.
